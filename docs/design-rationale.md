# 설계 근거 (2026-09-17)

왜 마커인가, 왜 카메라 기준인가, 대안은 무엇이었나. 스펙이 "무엇을 만드는가"라면 이 문서는 "왜 그렇게 골랐는가"다. 용어는 [용어집](glossary.md) 참조.

---

## 1. 전제: 차량 쪽은 바꿀 수 없다

자동차운반선에 실리는 차는 도로 자율주행의 "내 차"와 다르다.

- **상품이다.** 출고 전 신차. 흠집 하나가 클레임
- **남의 것이다.** 센서 부착은커녕 개조 자체가 불가
- **매번 다르다.** 한 배에 여러 브랜드·차종. 다음 항차엔 또 다른 차들
- **수천 대다.** 대형 PCTC 는 6,000 ~ 8,000 대급

터미널은 어떤 차가 올지 정하지 못한다. 따라서 **차량에 요구할 수 있는 것은 모든 차가 이미 가진 것뿐**이다.

| 센서 | 양산차 탑재율 | 쓸 수 있나 |
| --- | --- | --- |
| 전방 카메라 | 사실상 전부 (ADAS 법규) | **최소공통분모** |
| 휠 오도메트리 / IMU | 전부 (ESC 필수) | 보조 |
| 초음파 | 대부분 | 근거리만 |
| 레이더 | 흔함 | 정밀 측위엔 부적합 |
| 라이다 | 극소수 고급 트림 | 불가 |

**이 전제가 이후 모든 선택을 결정한다.** 센서를 좋게 만들 수 없으니, 바꿀 수 있는 쪽인 배와 지도에 투자해 같은 결과를 낸다.

## 2. 지도의 두 역할

논의 중 가장 자주 섞였던 두 질문을 분리한다.

| 질문 | 답하는 것 | 없으면 |
| --- | --- | --- |
| 어디로 가야 하나 | **지도** | 목표 자체가 없다 |
| 내가 지금 어디 있나 | **랜드마크** | 목표는 알지만 못 찾아간다 |

둘 다 필요하고 서로 대체되지 않는다. 지도 하나가 두 역할을 겸한다 — 목표(`parking_slots.target_pose`)를 정의하고, 그 목표를 찾아갈 기준점(`landmarks`)을 준다.

### 2.1 도로 자율주행이 지도 없이 되는 이유

도로에서 목표는 눈에 보인다. "차선 안에 있어라", "앞차와 거리를 유지해라" — 전부 시야 안에 물리적으로 존재한다. 빈자리를 찾아 넣는 자동주차도 같다.

선내 적재의 목표는 `PS-D3-047` 이고, 이것은 물리적 존재가 아니라 **약속**이다. 바닥에 선을 그어도 "이것이 47 번"이라는 의미는 지도에만 있다.

### 2.2 왜 지정된 자리여야 하나

"빈자리 아무 데나"가 성립하지 않는 이유:

1. **하역 순서** — 여러 항구를 돈다. 먼저 내릴 차가 안쪽에 있으면 바깥 차를 전부 뺐다 다시 넣어야 한다
2. **중량 배분** — 수천 대의 무게 분포가 트림·힐에 직결된다
3. **차종별 높이** — 갑판마다 `z_clear` 가 다르다
4. **공간 효율** — 임의 배치는 틈을 만든다. 한 대라도 더 싣는 것이 이 사업의 전부다

넷 다 차가 현장에서 눈으로 판단할 수 없다. 전부 사전 계획이고, 그 계획이 곧 지도다.

## 3. 측위 기준점: 왜 AprilTag 인가

### 3.1 랜드마크는 태그만이 아니다

랜드마크 = **지도에 좌표가 적혀 있고, 차가 보고 식별할 수 있는 고정점**. 노면 횡바도, 구획 번호 문자도, 변조 LED 조명도, 기둥 코너도 전부 랜드마크다. 질문은 "둘 것인가"가 아니라 "어떤 형태로 둘 것인가"다.

**절대 좌표는 공짜로 나오지 않는다.** 오도메트리는 상대 정보만 주고 드리프트한다. 어딘가에서 지도에 좌표가 적힌 무언가를 관측해야만 절대 좌표가 생긴다. GPS 도 사실 하늘에 깔아둔 랜드마크 시스템이다 — 실외에서 랜드마크가 필요 없어 보이는 것은 이미 누가 깔아놓았기 때문이다.

### 3.2 형태 비교

| 기준 | 노면 페인트 | 벽·기둥 마커 |
| --- | --- | --- |
| 비용 | 싸다 | 싸다 |
| 측량 | 선·면이라 번거로움 | 점이라 쉽다 |
| 고유 id | 차선은 모두 동일 | 코드가 박혀 있다 |
| 한 번에 얻는 정보 | 축 하나씩 | `r, θ, α` 3 축 동시 |
| 저조도 | 약함 | 재귀반사면 강함 |
| **적재 중 가려짐** | **치명적** | 높이 붙이면 안 가려짐 |

마지막 항목이 결정적이다. 선적은 차가 점점 늘어나는 과정이라, **정밀도가 가장 필요한 후반부에 바닥이 가장 안 보인다.** 역방향으로 나빠지는 구조다.

고유 id 도 크다. 선내는 갑판마다 구역마다 같은 모양이 반복되는데 차선은 어디서나 같은 흰 선이다. "3 갑판 좌현 7 번 차로"를 차선만으로는 알 수 없다.

### 3.3 대안 방식들

| 방식 | 절대 위치 | 방향 ψ | 선내 최대 난점 |
| --- | --- | --- | --- |
| **AprilTag 비전** | 직접 | 직접 | 부착·유지 비용 |
| 라이다 맵매칭 | 가능 | 가능 | 반복 구조에서 오정합 + **차량에 라이다가 없다** |
| UWB 앵커 | 가능 | **불가** | 방향을 따로 구해야 함 |
| 비전 SLAM | 재위치화 성공 시 | 조건부 | 적재로 장면이 변함 |

- **라이다 맵매칭**: ICP/NDT 는 대응점 탐색이 추가된 Gauss-Newton 이다. 마커는 id 가 있어 대응이 공짜(`map.TryGetValue(o.id)`)지만 라이다 점에는 이름표가 없다. 기둥 12 m·래싱 0.75 m 의 주기적 구조는 ICP 의 천적으로, 한 칸 밀린 자세에서도 잔차가 비슷해 오정합한다. 무엇보다 §1 에 걸린다
- **UWB**: 관측이 `r` 하나뿐이라 앵커 3 개 이상이 필요하고 **ψ 는 원리적으로 나오지 않는다.** 태그 2 개를 1.5 m 간격으로 달아도 각 태그 오차 10 cm 면 각도 오차가 약 3.8° 로 허용치(2°)를 넘는다
- **비전 SLAM**: 단색 도색 철판의 텍스처 부족, 반복 구조로 인한 오재위치화, 저조도, 그리고 **시야의 대부분이 매 항차 달라지는 다른 차**다. 지도를 만들 때는 빈 갑판이었는데 주행할 때는 차로 가득 차 있다

### 3.4 결론

선내 조건(반복 구조, 적재로 인한 시야 변화, 저조도, 카메라만 있는 차)을 모두 넣으면 **고유 id 를 가진 마커를 높은 곳에** 두는 것이 가장 튼튼하다. 태그 하나가 `r, θ, α` 를 모두 주므로 최소 관측으로 자세가 닫히고, 틀렸을 때 왜 틀렸는지 설명된다 — 어느 태그를 못 봤는지, 어느 태그 좌표가 틀렸는지.

페인트는 마커를 대체하지 않고 **보완**한다 (§5).

### 3.5 이 약속은 교체 가능하다

`Localizer` 는 AprilTag 을 모른다. 받는 것은 `Observation` 뿐이다:

```csharp
public struct Observation { public string id; public double r; public double thetaRad; public double alphaRad; }
```

"id 있는 무언가를 봤고 거리와 두 각도가 이렇다" — 그것이 전부다. 종이 태그든 페인트든 변조 LED 든 기둥 모서리든 무관하다. 약속을 바꾸면 `LandmarkSensor` 한 파일만 갈아끼우면 되고 추정 수학·주행·지도 포맷은 그대로다. **`Observation` 이 그 경계선이다.**

## 4. 마커를 실제로 놓는 법

### 4.1 순서가 반대다

설계 좌표대로 붙이고 그 값을 믿는 것이 아니라, **붙인 다음 측량해서 지도를 만든다.**

```
1. 기준망 구축      영구 control point 매설 + 레이저 트래커/토탈스테이션
2. 마커 부착        설계 좌표로 대략 부착 (이 단계는 정밀할 필요 없음)
3. 본 측량          TLS 스캔 + 마커 좌표 실측 (위치 + 법선 각도)
4. 피처 추출        포인트 클라우드 → 차로·구획·기둥 벡터화
5. 지도 발행        Ship Frame 좌표로 정리, 버전 부여, 배포
6. 검증             실차 주행으로 추정 오차 확인   ← 이 데모가 하는 것
7. 유지관리         개조·변형·훼손 시 부분 재측량
```

배는 블록 공법으로 짓고 용접하며 수축·변형이 생기므로 **설계 도면 좌표는 애초에 믿을 수 없다.**

**1 번이 가장 먼저이자 가장 어렵다.** 원점 `AP × 기선 × 중심선` 은 수학적 정의라 배 안에 그어져 있지 않다. 스캔을 아무리 정밀하게 해도 기준망에 묶이지 않으면 지도가 되지 못한다. 측량 작업량의 대부분이 여기이고, 배가 물에 떠 흔들리는 상태에서는 할 수 없다.

### 4.2 장비는 고르는 것이 아니라 겹쳐 쓴다

| 장비 | 정밀도 감각 | 커버리지 | 역할 |
| --- | --- | --- | --- |
| 레이저 트래커 | 수십 µm ~ mm | 수십 m, 가시선 | 기준점 네트워크 |
| 지상 라이다 정적 스캔(TLS) | mm ~ cm | 스캔당 수십 m | 본 측량 |
| 모바일/핸드헬드 SLAM | cm ~ 수십 cm | 넓고 빠름 | 개략도, 변화 탐지 |
| 토탈스테이션 | mm | 점 단위 | 마커 좌표 확정 |

SLAM 단독은 상용 정밀도에 못 미친다. 배는 길고(120 ~ 200 m) 갑판이 층층이 같은 모양이라 드리프트가 쌓이고 루프 클로저도 어렵다.

### 4.3 3D 모델과 지도는 다른 산출물이다

```
스캔 → 포인트 클라우드 ─┬→ 메시 (시각화·간섭검토용, 선택)
                       └→ 벡터 피처 추출 (차로·구획·마커·기둥) ← 지도
```

HD 지도는 배의 생김새가 아니라 **차가 알아야 할 것**만 골라 담은 벡터 레이어다. 점 수억 개짜리 메시는 차량이 실시간으로 쓰지 못한다. 메시는 편집을 돕는 배경이지 지도 자체가 아니다. M5b Task 7 이 선체를 `VehicleMap` 에서 짓도록 뒤집는 것도 **지도가 원본이고 모델이 파생물**임을 명확히 하기 위해서다.

### 4.4 남는 오차

| 오차원 | 크기 감각 | 대응 |
| --- | --- | --- |
| 부착 위치 측량 | mm ~ cm | 측량 정밀도 |
| **부착 각도(법선 φ)** | 도 단위로 쉽게 틀어짐 | `α = φ − ψ` 라 방향 추정에 직결. 위치보다 아프다 |
| 선체 변형 | 적재·온도·경년 | 주기적 재측량 |
| 마커 훼손·도색·가려짐 | — | 중복 배치, 관측 수 하한 |

마커를 3 cm 옆에 붙이는 것은 큰 문제가 아니지만 법선이 2° 틀어지면 마커 하나만 볼 때 방향 추정이 그대로 2° 틀어진다.

## 5. 카메라만 있는 차량을 위한 설계

마커를 쓰지 않거나 마커 사이를 메워야 할 때의 원칙: **차가 이미 검출하는 것으로만 지도를 기술한다.** 양산 비전 스택의 공통 출력은 차선·노면 표시·수직 구조물·자유공간 정도다.

### 5.1 오차 축마다 난이도가 다르다

`Judge` 가 오차를 세 축으로 나누는 것이 우연이 아니다.

| 축 | 허용오차 | 비전으로 | 수단 |
| --- | --- | --- | --- |
| 횡 `lat` | 0.15 m | 쉽다 | 차선·구획선까지 거리 |
| 방향 `heading` | 2° | 쉽다 | 선의 방향이 곧 답 |
| **종 `lon`** | 0.30 m | **어렵다** | 긴 직선에서 "얼마나 왔나"는 시각적으로 구별되지 않는다 |

따라서 설계는 이렇게 갈린다:

```
횡·방향  →  연속적 시각 추종 (차선을 계속 보며)
종       →  이산 앵커 (정지선·횡바를 지날 때마다 리셋) + 사이는 오도메트리
```

구간 경계를 종방향 앵커와 일치시키면 "앵커를 지났다 = 구간을 넘었다"가 시각으로 확인되어 관제 상태와 차량 인식이 자연히 동기화된다.

### 5.2 정밀도는 구간별로 차등한다

| 구간 | 필요 정밀도 | 수단 |
| --- | --- | --- |
| 램프 | 횡 ±0.3 m | 램프 가장자리 |
| 차로 주행 | 횡 ±0.5 m, 종 ±2 m | 차선 추종 + 횡바 앵커 |
| 이탈 ~ 대각 | 횡 ±0.3 m | 구획 열 경계선 |
| **마지막 5 m** | 횡 ±0.15 m, 방향 ±2° | 구획 경계선 + 번호 OCR + 초음파 |

**전 구간 고정밀은 불필요하다.** 접근 경로를 "차로 추종 → 이탈 → 45° 대각 → `FinalRunM` 직진"으로 나눠둔 현재 구조가 이 차등을 이미 반영한다.

### 5.3 그 밖의 수단

- **노면 페인팅** — 차가 이미 차선을 볼 줄 알아 새 인식 능력이 불필요. `B2` 레이어가 담을 자리. 단 적재가 진행되면 가려진다
- **변조 LED (VLC)** — 조명을 사람 눈에 안 보이는 주파수로 깜빡여 id 송출, 롤링 셔터로 디코딩. 천장이라 가려지지 않으나 차량 소프트웨어 지원이 필요
- **천장 구조 (MEP·빔)** — 적재와 무관하게 안 가려지는 유일한 영역이지만 양산차 카메라 화각이 전방이라 보이지 않는다. 인프라로 풀 수 없는 차량 제약
- **구조광 투영** — 프로젝터로 바닥에 패턴·숫자를 쏜다. 동적이고 마모가 없으며 기존 노면 인식 파이프라인을 그대로 쓴다

### 5.4 지도 포맷에 미치는 영향

마커 지도는 "점 + 법선"이면 충분하지만, 비전 기반이면 **어느 축이 잡히는가**를 함께 기술해야 한다:

```json
{ "id": "B2-0101", "kind": "lateral_bar", "polygon": [],
  "visual": { "width_m": 0.3, "constrains": ["lon"] } }
```

그래야 차가 "지금 lon 이 불확실하니 다음 횡바까지 오도메트리로 버틴다"를 판단할 수 있다.

## 6. 다중 차량 운용

### 6.1 수백 대가 동시에 달리지 않는다

램프가 1 ~ 2 개이므로 선적은 본질적으로 파이프라인이다. 동시 주행 차량은 많아야 수십 대다.

### 6.2 역할 분담

| 계층 | 담당 | 주기 |
| --- | --- | --- |
| 컨트롤 타워 | 슬롯 배정, 투입 순서, 구간 통행 허가 | 초 단위 |
| 차량 | 측위, 경로 추종, 정밀 주차, 긴급 정지 | 10 ~ 100 Hz |
| 인프라 | 노면 표시, 종방향 앵커, 통신 AP | 정적 |

**타워는 차를 운전하지 않는다.** 무선 지연·끊김 때문에 중앙에서 실시간 조향을 보내는 것은 위험하다. 현재 코드로 보면 타워가 `NextSlot()`, 차량이 `ApproachPath` + `LaneFollower` 이며 이미 분리되어 있다.

### 6.3 순서가 충돌 회피를 미리 푼다

`SlotGenerator` 의 채움 순서(선수 먼저, 좌현→우현)는 장식이 아니다. 모든 접근 경로가 목표의 선미 쪽에서 오므로 **`sequence_no` 순으로만 넣으면 경로가 겹치지 않음이 기하학적으로 보장된다.** 충돌 회피를 실시간 협상이 아니라 설계 시점에 해결한 것이다. 수백 대로 확장해도 원리는 같다.

### 6.4 폐색 구간

차로를 구간으로 자르고 한 구간에 한 대만 둔다. 철도 신호의 검증된 방식이다.

- 일방향 + 추월 없음이라 **데드락이 원리적으로 없다**
- 상태 공간이 작아 검증 가능하다
- 허가가 없으면 정지 — **통신이 끊겨도 기본 상태가 안전**하다
- 차당 초당 수십 바이트라 수백 대도 여유롭다

### 6.5 위치는 교차 검증한다

```
차 → 타워:    "B3 구간, 지도상 (62.4, −3.1), 신뢰도 높음"
인프라 → 타워: 천장 카메라가 B3 에 한 대 확인
```

자기 보고만 믿으면 차가 자기 위치를 틀리게 알 때 보고도 틀려 오류를 검출하지 못한다. 인프라 관측은 "어느 구간에 몇 대" 수준이면 충분하다.

### 6.6 진짜 어려운 것은 실패 회복

파이프라인은 한 대가 멈추면 뒤가 전부 막힌다.

| 실패 | 빈도 | 대응 |
| --- | --- | --- |
| 주차 실패 (`needs_adjust`) | 흔함 | 재시도 1 회 → 슬롯 스킵, 재배정 |
| 측위 상실 | 흔함 | 오도메트리로 짧게 버팀 → 초과 시 정지 |
| 차량 정지 | 가끔 | **뒤차 전부 정지.** 사람이 개입 |
| 통신 두절 | 가끔 | 현재 구간 끝에서 정지 |
| 예상 밖 장애물 | — | 차량 자체 AEB, 타워를 거치지 않음 |

사람이 없어지는 것이 아니라 역할이 바뀐다 — 수백 명의 운전기사가 소수의 관제·구조 인력이 된다. 그리고 **회복 시간이 곧 경제성**이다. 항만 체류 시간이 전부인 사업이라 한 대 멈출 때마다 10 분씩 잃으면 자동화 이득이 사라진다. 스킵·재배정 속도가 정밀도보다 중요할 수 있다.

### 6.7 통신

선체는 철판으로 된 패러데이 케이지다. 갑판 사이 전파가 거의 통하지 않아 **갑판마다 독립 AP** 가 필요하고, 기둥·차체가 다중경로를 만든다. 다만 필요한 대역폭은 작다 — **지도는 승선 전에 미리 내려받고**, 운용 중에는 배정과 허가만 오간다.

## 7. 이 데모가 가정하는 것

의도적으로 모델에 넣지 않은 것들. 스펙 §1.3 의 제외 목록과 함께 읽는다.

| 가정 | 현실 | 비고 |
| --- | --- | --- |
| **지도상 마커 위치 = 실제 부착 위치** | 측량 오차가 존재 | `Sense()` 가 `MapRefs` 를 관측 생성과 추정에 모두 쓴다. σ 를 0 으로 두면 오차가 0 으로 수렴하지만 현실에는 바닥이 있다 |
| 차량이 지도를 받아 쓸 표준 인터페이스가 있다 | 브랜드마다 다르고 표준이 없다 | 이 데모가 `vehicle-map v1` + REST 를 설계한 이유 |
| 인식기는 이미 있다 | — | 레이캐스트 감지 모델로 대체 |
| 한 대씩 순차 주행 | 수십 대 동시 | §6 은 미구현 |
| 마커는 항상 보인다 | 적재·훼손으로 가려짐 | 관측 0 개일 때의 거동은 `previous` 유지뿐 |

### 7.1 파킹: 지도 오차 모델링

`MapRefs`(지도값) 옆에 **실제 부착 위치** 딕셔너리를 두고, `Observe` 에는 실제값을, `Solve` 에는 지도값을 넘긴다. 슬라이더로 지도 오차 σ 를 주면 **센서를 아무리 좋게 해도 오차가 줄지 않는 바닥**이 보인다. 지금 구조에서 어렵지 않고(반나절), M5b 이후 M6 전에 넣을 만하다.

## 요약

1. **차량 쪽은 못 바꾼다** → 최소공통분모는 카메라 → 인프라와 지도에 투자한다
2. **지도는 목표를 정의하고 동시에 측위 기준을 준다** → 둘 중 하나도 뺄 수 없다
3. **절대 좌표는 공짜로 나오지 않는다** → 랜드마크는 형태를 고르는 문제이지 둘지 말지의 문제가 아니다
4. **선내 조건에서는 고유 id 를 가진 높은 마커가 가장 튼튼하다** → 페인트는 보완재
5. **정밀도는 구간별로 차등한다** → 마지막 5 m 에만 고정밀
6. **순서가 충돌을 미리 없앤다** → `sequence_no` 는 번호가 아니라 제약
7. **어려운 것은 측위가 아니라 실패 회복이다**
