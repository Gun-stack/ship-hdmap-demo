# M5c 설계 스펙 — 랜드마크 커버리지 분석과 배치 추천 (2026-09-17)

기본 스펙 `2026-09-15-ship-hdmap-demo-design.md` 의 M5 다음에 넣는 단계다. 브레인스토밍에서 확정한 결정만 담는다. 용어는 [용어집](../../glossary.md), 선택 근거는 [설계 근거](../../design-rationale.md) 참조.

- **M5b (앞)**: 부두 지오메트리, GPS, Quay Frame ↔ Ship Frame 전환
- **M5c (이 문서)**: 차가 실제로 지나가고 주차하는 곳마다 달성 가능한 추정 정밀도를 계산해 히트맵으로 보이고, 가상 마커로 실험하고, 다음에 놓을 위치를 추천한다
- **M6 (다음)**: 문서·시연

---

## 1. 범위

### 1.1 목적

"마커를 몇 개 어디에 둬야 하는가"에 도구가 답하게 한다. 지금은 마커를 놓고 **차를 돌려봐야** 배치가 좋은지 알 수 있고, 사각지대는 우연히 발견된다.

이것은 웹·3D 편집기가 존재해야 하는 이유이기도 하다. 시야각·거리·차폐·법선이 얽힌 가시성은 2D 도면으로 답할 수 없다.

### 1.2 들어가는 것

1. API: `CoverageAnalyzer`(순수 계산), `POST …/coverage`, `POST …/coverage/suggest`
2. 계산: 가시 마커 수 + **정보행렬에서 얻는 예상 오차 σ**, 안정성 마진
3. 평가 대상: 갑판 전체를 훑되 **구획 ∪ 차로 회랑** 셀만 지표와 목적함수에 센다 (§3.4)
4. 모드: 선적(ψ=0) / 하역(ψ=180) 각각 계산
5. What-if: 요청에 가상 마커를 실어 DB 를 건드리지 않고 재계산, 기존 마커 제외
6. 추천: 후보 면에 가상 마커를 놓아보는 그리디 탐색
7. 웹: 평면도 히트맵 레이어, 커버리지 패널(파라미터·요약·후보·추천), 확정 시 실제 피처로 저장

### 1.3 제외

- **Unity 변경 없음.** 계산은 전부 API 다. 3D 히트맵 오버레이는 넣지 않는다 — 커버리지의 값어치는 "3D 기하로 계산한다"이지 "3D 로 보여준다"가 아니다
- 차량 동역학·최소회전반경. 별개 주제이며 물리 엔진은 저속 선내에서 얻는 것이 없다
- 지도 오차(측량 오차) 모델. 파킹 유지 ([설계 근거](../../design-rationale.md) §7.1)
- 다중 차량, 동적 차폐(주차된 차). 지도에 없는 것은 계산하지 않는다
- 램프 위 커버리지. 램프는 경사라 2D 격자에 담기지 않는다
- 자동 배치 최적화(전역). 추천은 그리디 제안이고 결정은 사람이 한다
- 평면도 클릭으로 임의 위치에 후보를 놓는 것. 추천 목록에서 골라 담는 흐름으로 충분하다 (§6.3)

### 1.4 완료 기준

Deck 3 의 커버리지를 계산하면 **바깥 열 구획의 사각지대**가 히트맵과 숫자 양쪽에 나타난다. 마커가 `y = ±6.2` 한 줄에만 있어서 갑판 가장자리 쪽 구획에서는 시야각 90° 안에 마커가 들어오지 않는다.

현재 픽스처(마커 23 개, 기둥 18 개, 구획 76 개, 차로 1 개, `grid_m` 1.0)에서 확인된 값:

| 구간 | 셀 | 선적 blind | 하역 blind |
| --- | --- | --- | --- |
| 차로 (`\|y\| < 1.6`) | 476 | 1.7 % | 14.3 % |
| 1 열 (`\|y\| ≈ 3.4`) | 400 | 0.0 % | 6.0 % |
| 2 열 (`\|y\| ≈ 5.6`) | 40 | 0.0 % | 10.0 % |
| 3 열 (`\|y\| ≈ 7.9`) | 60 | 36.7 % | 30.0 % |
| **4 열 (`\|y\| ≈ 10.1`)** | 260 | **68.5 %** | **77.7 %** |
| 전체 (in-scope) | 1,236 | 16.8 % | 25.6 % |

구획 수가 M5b 의 진입 가능성 규칙 이후 136 → 76 으로 줄어 열별 셀 수가 그만큼 작다. 결론은 그대로다 — 바깥 열이 가장 나쁘고, 하역이 선적보다 나쁘다.

두 가지가 동시에 드러나야 한다:

1. **바깥 열 사각지대** — 선적 모드에서도 4 열 구획의 2/3 에서 자세를 잡을 수 없다. 갑판 용량의 1/3 에 해당한다
2. **하역 선미 사각지대** — 하역 모드에서 차로·1 열의 선미 구간(`x < 20`)에 blind 셀이 88 개 생긴다. 선적에서는 0 개다 (§7.2)

추천을 요청하면 이것들을 메우는 위치가 상위로 나오고, 그 후보를 적용하면 `blind_ratio` 가 떨어진다. 후보를 확정하면 실제 랜드마크로 저장되고 vehicle-map version 이 오른다.

§5 의 후보 규칙과 그리디를 실제 픽스처에 그대로 돌려 확인한 값 (`budget` 3, 격자 2.0, 후보 78 개):

| | 시작 | 1 순위 | 2 순위 | 3 순위 |
| --- | --- | --- | --- | --- |
| 선적 `blind_ratio` | 0.193 | 0.163 | 0.134 | **0.108** |
| 선적 바깥 열 `blind` | 0.855 | 0.742 | 0.629 | **0.500** |
| 하역 `blind_ratio` | 0.297 | 0.232 | 0.209 | **0.186** |
| 하역 바깥 열 `blind` | 0.984 | 0.968 | 0.903 | **0.823** |

**이 표의 시작값이 위 표와 다른 것은 격자 때문이다.** 위 표는 커버리지 패널의 기본인 `grid_m` 1.0 (선적 0.168), 이 표는 `suggest` 가 고정하는 격자 2.0 (선적 0.193)이다. 같은 배치를 다른 해상도로 잰 것이고, 브라우저에서 패널 숫자와 추천 결과를 나란히 볼 때 이 차이를 오차로 오해하기 쉽다. 두 표 모두 구획 76 개 기준이다 — 데모 DB 에 136 개가 남아 있다면 M5b 의 진입 가능성 규칙 이전에 생성된 것이니 `slots/generate` 를 다시 돌린다.

세 순위 모두 `gain` 이 양수이고 바깥 열이 단조로 좋아진다. 선적은 1~3 순위가 전부 기둥의 **선미쪽** 면(`φ = 180°`, `C-PILLAR-D3-017`·`008`·`004`), 하역은 1 순위가 선미 격벽(`(0, 6)`, `φ = 0°`)이고 2~3 순위가 기둥의 **선수쪽** 면(`φ = 0°`)이다 — §5.1.1 이 살려낸 면들이고, 바깥을 보는 면은 한 번도 뽑히지 않는다.

위 값은 모두 실제 엔드포인트를 호출해 잰 것이다.

## 3. 계산 모델

### 3.1 가시성

`LandmarkSensor.IsVisibleGeometric` 과 같은 세 조건이다. 기본값도 같게 둔다.

| 조건 | 기본값 |
| --- | --- |
| 거리 `r ≤ max_dist_m` | 25 m |
| 시야 `\|θ\| ≤ fov_deg/2`, `θ = wrap(atan2(dy,dx) − ψ)` | 90° |
| 법선 `\|wrap(atan2(−dy,−dx) − φ)\| ≤ max_view_angle_deg` | 70° |

차폐는 시선(셀 중심 ↔ 마커)과 **기둥 폴리곤 변의 2D 선분 교차**로 판정한다. 기둥은 바닥부터 천장까지라 2D 가 근사가 아니라 정확하다. MEP 는 천장에 있어 2D 로 보면 과하게 가리므로 차폐에서 제외한다(`SlotGenerator` 가 기둥만 장애물로 보는 것과 같은 취급).

마커가 기둥 면에 붙어 있으면 자기 기둥에 막히므로, 시선의 마커 쪽 끝을 0.05 m 줄여 검사한다 (`LandmarkSensor.Sense` 와 같은 처리).

### 3.2 예상 오차 σ

관측값 없이 야코비안만으로 정보행렬을 쌓는다. 잔차가 필요 없다 — 자세 추정이 아니라 **그 자세에서 얻을 수 있는 정밀도의 하한**을 구하는 것이기 때문이다.

가시 마커마다 (`dx = mx − x`, `dy = my − y`, `r = √(dx²+dy²)`):

```
jr = { −dx/r,   −dy/r,   0 }    w_r = 1/σ_r²
jt = {  dy/r²,  −dx/r²,  −1 }   w_θ = 1/σ_θ²
ja = {  0,       0,      −1 }   w_α = 1/σ_α²

A = Σ w · jᵀj            (3×3, Localizer.Accumulate 와 같은 식)
C = A⁻¹                  (Localizer.Solve3 와 같은 Cramer)
σ_xy  = √(C₀₀ + C₁₁)     [m]
σ_psi = √(C₂₂)           [rad] → 도로 변환해 응답
```

`σ_r`·`σ_θ`·`σ_α` 는 `Localizer.Weight` 와 같이 1e-6 으로 하한을 둔다.

**마커 1 개여도 σ 가 나온다.** 관측이 3 개(`r, θ, α`)이고 미지수가 3 개라 행렬이 정칙이며, `ClosedForm` 이 마커 하나로 풀리는 것과 같은 이유다. 값이 크게 나오는 것이 바로 보고 싶은 것이다.

특별 처리는 하나뿐이다: **`n = 0` 이거나 `|det A| < 1e-12` 면 `blind`** 로 취급하고 `sigma_xy`·`sigma_psi` 를 `null` 로 둔다(JSON 에서 생략).

`det` 가드는 방어용이고 실제로는 도달하지 않는다 — 기본 σ 에서 `w_θ ≈ 3,283` 이라 `det A` 가 10⁵ 규모다(픽스처 전 셀에서 최소 `1.095e+05`). 특이 케이스를 `blind` 와 합치는 이유는 지표와 색을 어긋나지 않게 하기 위해서다. 따로 두면 `blind_ratio` 에도 `weak_ratio` 에도 안 세지는데 화면에는 빨갛게 칠해진다.

### 3.3 안정성

절대값보다 허용오차 대비 여유가 읽기 쉽다. 기준값은 `ScenarioPlanner.Judge` 의 기본 허용오차와 같게 둔다.

```
margin_xy  = 0.15 / σ_xy         (tolerance.lat_m)
margin_psi = 2.0  / σ_psi_deg    (tolerance.heading_deg)
stability  = min(margin_xy, margin_psi)
```

셀 분류:

| 분류 | 조건 | 뜻 |
| --- | --- | --- |
| `blind` | `n = 0` 또는 `det A` 특이 | 치명. 위치를 잡을 수 없다 |
| `weak` | `stability < 1` | 허용오차를 못 채운다 |
| `ok` | `stability ≥ 1` | — |

**`weak_ratio` 는 정보가 줄 때 단조롭지 않다.** 마커를 빼거나 센서를 나쁘게 하면 `weak` 였던 셀이 `blind` 로 넘어가면서 `weak` 분자가 **줄어든다**. 실측: `omit` 으로 LM-0020·0021 을 빼면 선적 `weak` 가 0.6875 → 0.5375, `max_dist_m` 을 25 → 14 m 로 줄이면 85.4 % → 47.8 % 로 떨어진다. 배치가 나빠졌는지 볼 때는 항상 **`blind_ratio`** 를 본다 — 정보가 줄어들 때 이쪽은 단조로 오른다.

차로 위 `σ_xy` 는 0.2 ~ 0.34 m 로 `lat_m` 0.15 m 를 넘는 것이 정상이다 — 주행 중에는 그래도 되고 구획 가까이에서 좋아지면 된다. `weak` 는 결함이 아니라 관찰 대상이며, 결함은 `blind` 다.

### 3.4 격자와 평가 대상

갑판 윤곽의 bbox 를 `grid_m` 간격으로 훑고, **윤곽 안이며 기둥 밖인 셀**을 계산한다. 기본 `grid_m` 1.0 m — Deck 3(120 × 24 m)이면 2,880 셀이다.

그중 **차가 실제로 있을 수 있는 셀만 지표에 센다.** 이것을 `in_scope` 라 부르고, 조건은 둘 중 하나다:

1. 구획 폴리곤(`layer='B2'`) 안 — 차가 주차해야 하는 곳
2. 차로 중심선(`layer='A2'`)에서 `width_m/2` 이내 — 차가 지나가야 하는 곳

Deck 3 이면 2,880 셀 중 1,236 셀이 `in_scope` 다.

**왜 나누는가.** 갑판 가장자리·기둥 뒤 같은 곳은 차가 갈 일이 없으니 거기서 자세를 못 잡아도 상관없다. 그런데 면적으로는 그쪽이 더 넓어서, 전 갑판을 분모로 잡으면 지표가 그 잡음에 지배된다. 실제로 선적 모드 갑판 전체 `blind_ratio` 는 in-scope 로 좁힌 16.8 % 보다 훨씬 높고, 그 차이는 대부분 아무도 가지 않는 가장자리다. 더 나쁜 건 §5.2 의 목적함수가 `blind` 셀 수를 세므로 **그리디가 가장자리를 메우러 간다**는 것이다. 지표가 틀린 모집단에서 재면 추천은 정확하게 계산된 오답이 된다.

`in_scope` 가 지배하는 것:

- `blind_ratio`·`weak_ratio` 의 분모(`n_cells`)
- `worst`
- §5.2 그리디의 목적함수

`in_scope` 가 **바꾸지 않는 것**: `cells` 배열은 갑판 전체를 그대로 담는다. 히트맵은 전 갑판을 칠하고 out-of-scope 셀만 흐리게 그린다(§6.1). "가장자리는 원래 안 보이고 그래도 된다"를 보여주는 데 별도 모드가 필요 없다.

**`scope` 파라미터는 두지 않는다.** 셀마다 불리언 하나면 두 이야기를 다 할 수 있는데 모드를 만들면 요청 필드·분기·UI 토글·테스트가 두 벌씩 생긴다.

구획도 차로도 없는 갑판이면 `in_scope` 를 전부 참으로 둔다 — 재료가 없을 때 분모가 0 이 되는 것보다 낫고, 단위 테스트가 맨 사각형 갑판을 그대로 쓸 수 있다.

셀 중심 높이는 `eye_height_m`(기본 1.2 m, `LandmarkSensor` 와 동일)이지만 가시성 계산은 2D 이므로 높이는 차폐에 쓰지 않는다. 마커와 차량이 같은 갑판에 있다는 전제다.

### 3.5 모드

FOV 90° 라 **차량이 보는 방향에 따라 가시 마커가 완전히 달라진다.** 단일 ψ 고정은 틀린 모델이다.

| 모드 | ψ | 근거 |
| --- | --- | --- |
| `load` | 0° | 차로가 선수 방향, 구획 `heading_deg` 가 전부 0° |
| `unload` | 180° | `DeparturePath` 의 마지막 구간이 선미 방향 |

법선이 차로를 향한 측면 마커(LM-0001 ~ 0018)는 주행 방향과 무관하게 대칭으로 보이지만, 끝단 마커는 그렇지 않다. 픽스처의 끝단 마커 4 개가 모두 `φ = 180°` 이고, 그중 **선미 끝단의 LM-0022·LM-0023 은 두 모드 모두에서 아무 데서도 보이지 않는다.** 갑판이 `x ≥ 0` 인데 법선이 −x 를 보므로 어느 갑판 지점에서 봐도 법선 조건 70° 를 못 넘긴다 (전 셀 검사에서 가시 지점 0 개, 같은 φ 의 선수 마커 LM-0020 은 411 개). 마커 두 개가 지도에 있는데 쓰이지 않는 것이고, 그래서 하역 시 선미가 비어 있다 (§7.2).

## 4. API

### 4.1 커버리지

```
POST /api/datasets/{ds}/decks/{deck}/coverage
{
  "mode": "load",                  // load | unload. 기본 load
  "grid_m": 1.0,
  "fov_deg": 90, "max_dist_m": 25, "max_view_angle_deg": 70,
  "sigma_r": 0.2, "sigma_theta": 1, "sigma_alpha": 2,     // 각도는 도
  "extra_landmarks": [ { "x": 60.0, "y": -6.2, "phi_deg": 90 } ],
  "omit": ["LM-0003"]
}
→ {
  "deck": "D3", "mode": "load", "grid_m": 1.0,
  "bbox": [x0, y0, x1, y1],
  "n_cells": 1236, "n_drawn": 2880,
  "blind_ratio": 0.1683, "weak_ratio": 0.8317,
  "worst": { "x": 4.5, "y": 0.5, "n": 2, "sigma_xy": 0.41, "stability": 0.37 },
  "other_mode": { "mode": "unload", "blind_ratio": 0.2557, "weak_ratio": 0.7314 },
  "cells": [ { "x": 4.5, "y": 0.5, "n": 2, "sigma_xy": 0.235, "sigma_psi": 0.94, "stability": 0.64, "in_scope": true } ]
}
```

- 본문 전체가 선택이다. 없으면 기본값으로 계산한다
- `extra_landmarks` 는 DB 에 저장하지 않는다. `size_m` 은 가시성에 쓰지 않으므로 받지 않는다
- `omit` 은 기존 랜드마크를 계산에서 뺀다. "이걸 떼면 얼마나 나빠지나"도 실험이다
- **`n_cells` 는 `in_scope` 셀 수이고 두 비율의 분모다. `n_drawn` 은 `cells` 배열의 길이(갑판 전체)다.** 둘은 다르다
- `cells` 는 out-of-scope 셀과 `n = 0` 인 셀도 포함한다(`sigma_*` 생략). `in_scope` 는 **false 일 때만** 실린다 — 대부분의 셀에서 키 하나를 아낀다. 응답 크기는 2,880 셀 기준 약 200 KB
- `worst` 는 **`in_scope` 이면서 `blind` 가 아닌 셀 중 `stability` 가 가장 낮은 것**이다. `blind` 셀은 σ 가 없어 순서를 매길 수 없고 `blind_ratio` 가 이미 그것을 센다. 해당 셀이 없으면 `worst` 는 생략된다
- `other_mode` 는 반대 모드의 요약만 같은 파라미터로 함께 계산한 것이다. 셀 배열은 없다. 두 모드를 나란히 보여주는 데 왕복이 두 번 필요하지 않게 한다

### 4.2 추천

```
POST /api/datasets/{ds}/decks/{deck}/coverage/suggest
{ "mode": "unload", "budget": 3, ...(커버리지와 같은 파라미터) }
→ {
  "deck": "D3", "mode": "unload", "budget": 3, "grid_m": 2.0,
  "before": { "blind_ratio": 0.3524, "weak_ratio": 0.6476 },
  "after":  { "blind_ratio": 0.19, "weak_ratio": 0.71 },
  "suggestions": [
    { "rank": 1, "x": 12.0, "y": -6.2, "phi_deg": 0, "mounted_on": "Pillar-D3-02-S",
      "blind_after": 0.28, "weak_after": 0.66, "gain": 0.072 }

}
```

`suggestions` 는 누적이다 — 2 순위는 1 순위를 놓은 상태에서 계산한다. `budget` 기본 3, 최대 10. `gain` 은 그 순위를 채택해서 줄어든 **`blind_ratio` 의 양**이다.

**`suggest` 는 격자를 2.0 m 로 고정한다** (요청의 `grid_m` 을 무시하고 응답에 실제 쓴 값을 싣는다). 추천이 고르는 것은 기둥 면이나 격벽 면이라 1 m 해상도로 훑을 이유가 없다 — 면의 간격 자체가 그보다 훨씬 성기다. 계산량이 줄어드는 것은 부수 효과다.

## 5. 추천 알고리즘

### 5.1 후보 면

마커는 아무 데나 붙지 않는다. 후보는 **구조물의 면**이다.

1. 기둥 폴리곤(`layer='C' kind='pillar'`)의 각 변 → 중점, 법선은 **기둥 바깥** 방향
2. 갑판 윤곽의 각 변(벌크헤드) → 중점, 법선은 **갑판 안쪽** 방향

두 경우 모두 "면에서 차량이 있는 쪽"이다. 링의 감김 방향에 기대지 않고, 변의 두 수직 후보 중 **폴리곤 안쪽 점에서 먼 쪽**(기둥) / **가까운 쪽**(갑판 윤곽)을 고른다. 판정은 `Rings.contains` 로 중점에서 0.1 m 나아간 점이 폴리곤 안인지 본다.

**긴 변은 `face_spacing_m`(12 m, 픽스처의 기둥 간격) 마다 나눈다.** 변당 중점 하나면 갑판 윤곽의 120 m 짜리 긴 변이 `x = 60` 한 점이 되어 격벽이 사실상 후보에서 빠진다. 기둥 변은 0.6 m 라 한 점 그대로다.

### 5.1.1 중복 배제 — 거리만 보면 안 된다

**기존 마커에서 `2 m` 이내이면서 법선 방향이 `45°` 이내로 같은 면**만 제외한다. 거리만으로 자르면 후보가 거의 다 사라진다.

픽스처의 기둥은 0.6 × 0.6 m 인데 마커가 이미 그 기둥에 붙어 있다. 기둥 `P3` 은 `x ∈ [11.7, 12.3]`, `y ∈ [−6.8, −6.2]` 이고 마커 LM-0001 은 `(12.0, −6.2)` — **안쪽 면 중점과 정확히 같은 자리**다. 네 면까지의 거리가 0 ~ 0.6 m 라 거리만 보면 **네 면이 전부 걸러진다.** Deck 3 전체로는 기둥 18 개의 72 개 면이 모두 사라지고 갑판 윤곽 4 개만 남아, 바깥 열 사각지대(§1.4)를 메울 후보가 **하나도 없게 된다.**

방향까지 보면 같은 기둥에서 세 면이 살아난다:

| 면 | 중점 | 법선 | 마커와의 방향 차 | 결과 |
| --- | --- | --- | --- | --- |
| 안쪽 | `(12.0, −6.2)` | `+90°` | 0° | 제외 — 같은 자리 같은 방향 |
| 바깥쪽 | `(12.0, −6.8)` | `−90°` | 180° | 후보 |
| **선미쪽** | `(11.7, −6.5)` | `180°` | 90° | 후보 — 선적에서 쓰인다 |
| **선수쪽** | `(12.3, −6.5)` | `0°` | 90° | 후보 — 하역에서 쓰인다 |

Deck 3 이면 기둥 18 × 3 + 윤곽 (10 + 2) × 2 = **78 개**다.

**정작 그리디가 고르는 것은 측면(선미·선수) 면이다.** 바깥쪽 면(`φ = ±90°`)은 직관적이지만 시야한계 70° 때문에 좁은 원뿔만 밝힌다. 선적 모드(ψ=0)에서 차는 앞을 보므로 **자기보다 앞에 있으면서 뒤를 보는** 마커가 필요하고, 그것이 `φ = 180°` 인 선미쪽 면이다. 하역은 대칭으로 선수쪽 면이다. 세 면을 다 살려야 하는 이유가 여기 있다 — 어느 면이 이길지는 모드가 정하며, 거리만으로 자르면 셋 다 잃는다.

부착 높이는 후보 생성에 쓰지 않는다. 실제 저장 시 기존 마커와 같은 높이(`z_surface + 1.2`)를 쓴다.

### 5.2 그리디

```
for i in 1..budget:
    최선 = null
    for 후보 c in 후보목록:
        점수 = score(현재 마커 + 채택된 것들 + c)
        최선 = 더 나은 쪽
    채택 += 최선;  후보목록 -= 최선
```

**목적함수** — `in_scope` 셀만 세고, 사각지대를 먼저 없앤 다음 약한 셀을 줄인다:

```
score = blind_in_scope × 10 + weak_in_scope      (작을수록 좋다)
```

`× 10` 은 사각지대 하나가 약한 셀 열 개보다 나쁘다는 뜻이다. 사각지대는 위치를 못 잡는 것이고 약한 셀은 정밀도가 모자란 것이라 종류가 다르다.

out-of-scope 셀은 세지 않을 뿐 아니라 **평가 자체를 건너뛴다.** 추천 경로에는 히트맵이 필요 없으므로 σ 를 구할 이유가 없다. Deck 3 · 격자 2.0 이면 720 셀 중 459 셀만 돈다.

### 5.3 성능

후보 78 개 × `budget` 3 × 격자 2.0 의 in-scope 459 셀 × 마커 25 개 → 대략 270 만 회 가시성 검사. Java 로 수백 ms 다. `budget` 10 이면 그 3 배가 되므로 상한을 10 으로 둔다.

`ponytail:` 후보마다 갑판을 다시 훑는다. 정보는 단조 증가하므로 이미 `ok` 인 셀은 마커를 더해도 `ok` 로 남고, 원리상 현재 `blind`·`weak` 인 셀만 다시 보면 된다. 더 나아가 셀마다 baseline `A` 행렬을 캐시해 두면 후보당 3 행만 더하면 되어 마커 수 곱이 사라진다. 격자 2.0 고정으로 이미 충분히 빠르므로 지금은 하지 않는다. 전역 최적이 필요해지면 업그레이드 경로는 시설 입지(facility location) 근사다.

## 6. 웹

### 6.1 배치

편집 모드 안에 둔다. 새 탭을 만들지 않는다.

- **왼쪽 `MiniMap`**: 히트맵을 갑판 윤곽 아래 레이어로 그린다. 셀마다 `<rect>`, 색은 `stability` — `blind` 는 빨강, `weak` 는 주황~노랑, `ok` 는 초록 계열. **out-of-scope 셀은 같은 색을 불투명도 0.18 로 그린다** — "여기는 안 보이지만 차가 갈 일도 없다"가 한눈에 읽히고, 지표에서 뺀 것이 무엇인지도 같이 보인다. 기존 피처는 그 위에 그대로 그린다
- **오른쪽 `CoveragePanel`**: 편집 모드의 `LoadPanel` 아래

커버리지를 계산할 갑판은 **`MiniMap.pickDeck` 과 같은 규칙**으로 고른다. 세 갑판의 면적이 같아 `deckFilter = "all"` 일 때 임의로 고르면 평면도가 D1 을 그리는데 히트맵은 D3 가 깔린다.

`grid_m` 1.0 이면 `<rect>` 2,880 개다. SVG 로 감당 가능하며, 느려지면 `grid_m` 을 올리는 것이 먼저다.

### 6.2 패널

| 구역 | 내용 |
| --- | --- |
| 모드 | 선적 / 하역 토글. 응답의 `other_mode` 로 두 모드의 `blind_ratio` 를 나란히 표시 |
| 파라미터 | `grid_m`, `fov_deg`, `max_dist_m`, `max_view_angle_deg`, σ 3 개. 슬라이더는 **놓을 때만** 호출한다(`DrivePanel` 의 `SetNoise` 와 같은 이유) |
| 요약 | `blind_ratio`(in-scope 셀 수와 함께), `weak_ratio`, 최악 지점 좌표 |
| 후보 | 가상 마커 목록. 추천에서 담기, 개별 삭제, 전체 비우기 |
| 추천 | `budget` 입력, 실행 버튼, 결과 목록(순위·좌표·gain). 각 항목에 "후보로 담기" |
| 확정 | 후보 전체를 실제 랜드마크로 저장 |

**파라미터 초기값은 API 기본값과 같은 값으로 채워 둔다.** 비워 두면 슬라이더가 최솟값에 서 있는데 서버는 기본값으로 계산해서, 화면 숫자와 실제 계산이 처음부터 어긋난다.

`blind_ratio` 옆에는 분모를 같이 적는다 — `16.8 % (1,236 셀 중)`. 갑판 전체가 아니라는 것이 숫자만 봐서는 드러나지 않는다.

기존 마커 제외(`omit`)는 `LayerTree` 의 LM 항목 체크박스로 한다.

### 6.3 후보 배치와 확정

후보는 **추천 결과에서 골라 담는다.** 평면도 클릭으로 임의 위치에 놓는 기능은 넣지 않는다 — 후보 면 목록을 받는 엔드포인트가 따로 필요하고, 기존 피처에 이미 `onClick` 선택 핸들러가 붙어 있어 SVG 클릭을 더하면 한 번 클릭에 선택과 배치가 같이 일어난다. 임의 위치 배치가 필요해지면 `GET …/coverage/faces` 를 더하고 그때 클릭 핸들러를 넣는다.

**확정**은 후보마다 `POST /features` 를 호출한다. `layer: "LM"`, `kind: "apriltag"`, `props` 는 `PropertyForm` 이 만드는 것과 같은 모양(`family`, `code`, `normal`, `size_m`, `mounted_on`)이다. `code` 는 기존 최대 + 1 부터 부여한다. 저장 후 `load()` 로 새로고침하고 커버리지를 다시 계산한다.

## 7. 테스트

### 7.1 단위 (Java)

1. **마커 1 개로 σ 가 나온다** — 정칙이고 `sigma_xy` 가 유한하다
2. **관측 0 이면 blind** — `sigma_*` 가 없고 `blind_ratio` 에 들어간다
3. **기하가 정밀도를 바꾼다** — 같은 거리의 마커 3 개를 (a) 한쪽에 몰아서 (b) 둘러싸게 배치하면 개수가 같아도 (b) 의 `sigma_xy` 가 더 작다. **개수 세기가 순진하다는 것을 못 박는 테스트다**
4. **센서 σ 가 커지면 예상 오차도 커진다** — 단조성
5. **차폐** — 시선에 기둥을 놓으면 그 마커가 빠진다. 마커가 붙은 기둥 자신은 가리지 않는다
6. **`omit` / `extra_landmarks`** — 계산에 반영되고 DB 는 변하지 않는다. 마커를 빼면 **`blind_ratio` 가 오른다**(`weak_ratio` 로 재면 안 된다 — weak 였던 셀이 blind 로 넘어가면서 weak 분자가 오히려 줄어든다. 픽스처에서 LM-0020·0021 을 빼면 선적 `weak` 가 0.6875 → 0.5375 로 떨어진다)
7. **`in_scope` 가 분모를 바꾼다** — 구획·차로를 넘기면 `n_cells < n_drawn` 이고 비율이 달라진다. 둘 다 비면 `n_cells == n_drawn`
8. **추천 단조성** — 채택할 때마다 `score` 가 줄거나 같다
9. **추천이 사각지대를 먼저 없앤다** — 사각지대 하나를 없애는 후보와 약한 셀 다섯을 줄이는 후보가 있으면 전자를 고른다
10. **추천이 out-of-scope 를 무시한다** — 갑판 가장자리만 메우는 후보와 구획을 메우는 후보가 있으면 후자를 고른다

### 7.2 회귀 (Java)

두 개다. 둘 다 **결함을 고정하는 것이 아니라 도구가 결함을 찾아냄을 고정한다.** 나중에 마커를 추가해 메우면 이 테스트들을 "메워졌다"로 뒤집는다.

1. **바깥 열 사각지대.** 현재 픽스처의 Deck 3, `mode: "load"` 에서 `|y| > 9` 인 in-scope 셀의 `blind` 비율이 0.5 를 넘는다 (실측 0.685). 같은 조건의 차로(`|y| < 1.6`)는 0.05 미만이다 (실측 0.017). 마커가 `y = ±6.2` 한 줄뿐이라 바깥 열이 FOV 밖으로 나가기 때문이다
2. **하역 선미 사각지대.** `mode: "unload"` 에서 `x < 20` 인 in-scope 셀에 `blind` 가 존재한다 (실측 88 셀). 같은 구간이 `load` 에서는 없다 (실측 0 셀). 선미 끝단 마커 LM-0022·0023 이 어느 방향에서도 안 보여서(§3.5) 선미로 달릴 때 정면에 잡히는 마커가 없기 때문이다

### 7.3 웹 (Vitest)

1. `stability` → 색 매핑이 경계값에서 맞다 (`blind`, `stability = 1`)
2. out-of-scope 셀의 불투명도가 낮다
3. 요약 숫자 포맷 (`blind_ratio` 를 백분율로)

### 7.4 브라우저 검증

1. Deck 3 선적 커버리지를 계산하면 히트맵이 뜨고, **바깥 열 구획이 빨갛다.** 가장자리는 같은 빨강이지만 흐리게 칠해져 구분된다
2. 하역으로 토글하면 선미 구간이 추가로 빨갛게 바뀌고 `사각지대` 값이 오른다
3. 추천 3 개를 요청하면 바깥 열이나 선미를 메우는 위치가 나온다
4. 담고 재계산하면 `blind_ratio` 가 떨어진다
5. 확정하면 랜드마크가 저장되고 3D 에 나타나며 vehicle-map version 이 오른다
6. `max_dist_m` 을 15 로 줄이면 **`blind_ratio` 가 오른다** (25 m 에서 16.8 %, 14 m 에서 52.1 %). `weak_ratio` 로 재면 안 된다 — 아래 §3.3 의 단조성 주의
7. 흘수·횡경사를 바꿔도 커버리지가 **변하지 않는다** (Ship Frame 불변의 확인)
8. 갑판 필터를 `전체` 로 두어도 평면도가 그리는 갑판과 히트맵의 갑판이 같다

## 8. 결정과 이유

| 결정 | 이유 |
| --- | --- |
| 지표를 개수가 아니라 σ 로 | 마커 3 개가 한쪽에 몰리면 2 개가 둘러싼 것보다 나쁘다. 픽스처에서 실제로 역전이 나온다(x=20 n=3 σ 0.278 vs x=116 n=2 σ 0.159) |
| 분모를 구획 ∪ 차로로 | 갑판 전체로 재면 아무도 가지 않는 가장자리가 통계를 지배하고(in-scope 16.8 % 와의 차이 대부분이 가장자리), 목적함수가 `blind` 셀을 세므로 그리디가 거기를 메우러 간다. 좁히면 숫자가 그대로 결론이 된다 |
| `scope` 모드 대신 `in_scope` 불리언 | 셀마다 불리언 하나로 "지표는 좁게, 그림은 넓게"가 동시에 된다. 모드를 만들면 요청 필드·분기·UI 토글·테스트가 두 벌씩 생긴다 |
| 계산을 API 에서 | `SlotGenerator` 와 같은 패턴, 단위 테스트, 추천의 계산량 |
| 링 기하를 `geo/Rings` 로 | `contains`·`bbox` 가 `SlotGenerator` 에 이미 있다. 복사하면 두 벌이 갈라진다 |
| 차폐를 2D 로 | 기둥은 바닥부터 천장까지라 근사가 아니다. Unity 물리로 얻는 추가 정확도가 없다 |
| 모드를 파라미터로 | FOV 90° 에서 ψ 고정은 틀린 모델. 선적만 보면 하역 사각지대를 놓친다 |
| What-if 를 요청 본문으로 | DB 를 더럽히지 않고 실험한다. 확정은 별도 행동이다 |
| 추천을 그리디로 | 전역 최적은 과하다. 결정은 사람이 하고 도구는 제안한다 |
| 중복 배제를 거리 + 법선으로 | 거리만 보면 마커가 붙은 기둥의 네 면이 다 걸러져 Deck 3 후보가 4 개로 줄고, 바깥 열을 메울 수단이 없어진다 (§5.1.1) |
| 긴 변을 12 m 마다 분할 | 변당 중점 하나면 120 m 격벽이 `x = 60` 한 점이라 후보에서 빠진다 |
| 추천 격자를 2.0 m 고정 | 고르는 대상이 구조물 면이라 1 m 해상도가 의미 없다. 계산량 감소는 부수 효과 |
| 평면도 클릭 배치 없음 | 후보 면 엔드포인트가 따로 필요하고, 기존 피처의 `onClick` 과 버블링으로 겹친다. 추천에서 골라 담는 흐름으로 완료 기준이 충족된다 |
| 3D 히트맵 없음 | 커버리지는 3D 로 **계산**해야 하지만 2D 로 **표시**하면 충분하다. 무선 커버리지 맵도 2D 다 |
| 선박 자세 슬라이더 없음 | Ship Frame 이 불변이라 결과가 변하지 않는다. 불변성 확인은 §7.4-7 로 충분하다 |
